# Глава 3. Data Pipelines и оркестрация

## Цели главы

- Понять устройство Data Pipeline  
- Различить ETL/ELT и Batch/Streaming  
- Уметь проектировать DAG и оркестрацию

---

## 3.1. Понятие Data Pipeline

**Data Pipeline** — автоматизированная последовательность шагов, которая перемещает и преобразует данные от источников к потребителям.

Пайплайн отвечает на вопросы:

- *что* запускается;  
- *в каком порядке*;  
- *когда*;  
- *что считать успехом/неуспехом*;  
- *как повторить* при сбое.  

Пайплайн ≠ один скрипт. Это управляемый процесс с зависимостями, наблюдаемостью и владельцем.

---

## 3.2. ETL и ELT

| | **ETL** | **ELT** |
|---|---------|---------|
| Порядок | Extract → Transform → Load | Extract → Load → Transform |
| Где transform | Внешний движок / сервер | В хранилище (SQL/dbt) |
| Когда удобен | Слабое DWH, жёсткая очистка до загрузки | Современные облачные/мощные DWH |
| Плюс | В lake/DWH только «чистые» данные | Гибкость, RAW сохраняется, быстрее итерации |

В DataOps чаще **ELT + слой RAW**: можно переиграть трансформации без повторного extract из хрупкого источника.

---

## 3.3. Batch и Streaming

**Batch** — порциями по расписанию (раз в час / день).

- простота;  
- предсказуемая нагрузка;  
- подходит для большинства отчётов.  

**Streaming** — непрерывная обработка событий.

- низкая задержка;  
- сложнее exactly-once, порядок, late data;  
- Kafka / Flink / Spark Structured Streaming.  

Гибрид: микробатчи каждые N минут — часто достаточный компромисс.

Для курсового проекта достаточно **batch**; streaming — доп. задание.

---

## 3.4. DAG и зависимости

**DAG** (Directed Acyclic Graph) — ориентированный ациклический граф задач.

```text
load_customers ──┐
load_orders ─────┼──→ raw_quality_check → dbt_run → dbt_test → publish
load_returns ────┘
```

Правила:

- нет циклов;  
- задача стартует после успешных upstream;  
- явные зависимости лучше «большого скрипта со sleep».  

Граф делает сбой **локализуемым**: упал `load_returns` — не запускаем dbt на неполных данных (или запускаем с политикой, осознанно выбранной).

---

## 3.5. Оркестрация процессов

**Оркестратор** управляет:

- расписанием;  
- зависимостями;  
- ретраями;  
- таймаутами;  
- логированием;  
- статусами runs.  

Оркестратор **не обязан** сам считать SQL — он запускает задачи (Python, dbt, Spark-job).

Без оркестрации команда живёт на cron и «кто-то перезапустит».

---

## 3.6. Airflow / Dagster

### Apache Airflow

- DAG = Python-код;  
- операторы (Bash, Python, Docker, Kubernetes);  
- UI со статусами и логами;  
- де-факто стандарт в индустрии.  

Сильные стороны: экосистема, знакомство рынка.  
Слабые: локальная сложность setup, исторически «толстые» DAG.

### Dagster

- акцент на **software-defined assets**;  
- типизация, тесты, лучшая модель «данных как активов»;  
- удобен для Analytics as Code mindset.  

В курсе рекомендуется **Airflow** (как в ТЗ); Dagster — допустимая замена при сохранении требований.

---

## 3.7. Kafka и событийная архитектура

**Apache Kafka** — брокер событий: producers пишут в topics, consumers читают.

Роль в DataOps:

- decoupling источников и потребителей;  
- буфер при пиках нагрузки;  
- основа near-real-time пайплайнов;  
- CDC-потоки (Debezium → Kafka → DWH).  

Паттерны:

- event-driven ingestion;  
- fan-out: одно событие → несколько витрин / сервисов.  

Сложности: схема сообщений (Schema Registry), идемпотентные consumers, мониторинг lag.

## 3.8. Retry, backfill, scheduling

### Retry

Повтор при временных сбоях (сеть, API 503).

- ограничить число попыток;  
- exponential backoff;  
- не ретраить заведомо логические ошибки без фикса.  

### Scheduling

- cron / timetable;  
- учёт timezone;  
- data interval (за какой период считаем run).  

### Backfill

Пересчёт истории за прошлые даты (после фикса бага в SQL).

Требования:

- идемпотентные модели (incremental корректно обрабатывает даты);  
- понимание влияния на downstream;  
- лимиты параллелизма, чтобы не убить warehouse.  

### Timeout

Задача не должна висеть бесконечно: timeout + алерт.

---

## 3.9. Надёжность пайплайнов

Чеклист надёжности:

| Практика | Зачем |
|----------|-------|
| Идемпотентность | Безопасный rerun / backfill |
| Явные зависимости | Не строить MART на пустом RAW |
| DQ gates | Не публиковать брак |
| Алерты | Быстрый MTTR |
| SLA/SLO | Договорённость с бизнесом |
| Документация runbook | Что делать при падении |
| Разделение fail-fast / soft-fail | Критичные vs предупреждения |

Антипаттерны:

- «всё в одном task»;  
- игнор failed tasks «потому что завтра само»;  
- ручной backfill без записи в Git/тикет.

## Пример учебного DAG

```text
START
  → load_olist_tables
  → load_dummyjson_inventory
  → load_returns_files
  → raw_quality_check
  → dbt_run
  → dbt_test
  → publish_marts / refresh_bi
END
```

Настройки: `retries=2`, `execution_timeout`, логи в Airflow UI, fail при падении dbt test.

---

## Ключевые выводы

1. Pipeline — управляемый граф шагов, не разовый скрипт.  
2. ELT + RAW хорошо стыкуется с DataOps и dbt.  
3. Оркестратор даёт зависимости, schedule, retry, видимость.  
4. Надёжность = идемпотентность + тесты + мониторинг + runbook.
