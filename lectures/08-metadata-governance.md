# Глава 8. Metadata, Data Lineage и Governance

## Цели главы

- Понять виды metadata и роль catalog  
- Уметь объяснить lineage показателя  
- Знать основы governance, ownership и доступа  
- Ориентироваться в DataHub / OpenMetadata / Purview  

---

## 8.1. Metadata

**Metadata** — данные о данных: что это за таблица, откуда, кто владелец, какая свежесть, какие тесты.

Без metadata платформа — «чёрный ящик с таблицами».

Metadata должна быть:

- актуальной (собирается автоматически, где возможно);  
- доступной для поиска;  
- связанной с кодом и пайплайнами.  

---

## 8.2. Technical и Business Metadata

| Technical | Business |
|-----------|----------|
| Имя таблицы, колонки, типы | Бизнес-определение метрики |
| Партиции, объём, DDL | Владелец домена |
| Job, schedule, path | Критичность для отчётности |
| Тесты, SLI | Глоссарий терминов («Active Customer») |

Обе стороны нужны: техника без бизнеса → никто не понимает смысл; бизнес без техники → нельзя отладить.

---

## 8.3. Data Catalog

**Data Catalog** — система discovery и документации активов данных.

Возможности:

- поиск таблиц и отчётов;  
- описания и теги;  
- владельцы;  
- иногда lineage и профили.  

Примеры: DataHub, OpenMetadata, Amundsen, Atlan, Purview.

В малом проекте роль catalog частично закрывают **dbt docs** + README.

---

## 8.4. Data Lineage

**Lineage** — происхождение данных: откуда колонка/таблица и через какие трансформации.

Пример из курса:

```text
Revenue
  ↑ mart_sales_daily
  ↑ fact_orders
  ↑ stg_orders
  ↑ raw_orders
  ↑ PostgreSQL.orders (Olist)
```

Зачем:

- impact analysis («что сломается, если убрать колонку»);  
- расследование инцидентов;  
- compliance и доверие.  

Автоматический lineage: dbt `ref`/`source`, OpenLineage, каталоги.

---

## 8.5. Ownership

У каждого критичного актива — **владелец**:

- кто отвечает за качество и SLA;  
- кого звать при инциденте;  
- кто аппрувит контракт.  

Модели:

- data owner (бизнес-ответственность);  
- data steward (качество и правила);  
- technical owner (pipeline/код).  

«Таблица без владельца» = таблица-сирота.

---

## 8.6. Data Governance

**Data Governance** — правила, роли и процессы управления данными:

- стандарты именования;  
- политики качества;  
- классификация данных;  
- lifecycle и retention;  
- согласование критичных изменений.  

Governance не равен «запретить всё». Зрелый governance **ускоряет** работу за счёт ясности правил.

---

## 8.7. RBAC и доступ к данным

**RBAC** — доступ по ролям:

- аналитик читает mart, не пишет в RAW;  
- инженер деплоит пайплайны;  
- стажёр — только anonymized sample.  

Принцип least privilege.  
Отдельно: доступ к prod vs dev, маскирование в non-prod.

---

## 8.8. PII и чувствительные данные

**PII** (Personally Identifiable Information) — данные, идентифицирующие человека.

Практики:

- классификация колонок;  
- маскирование / токенизация;  
- минимизация сбора;  
- аудит доступа;  
- политики хранения и удаления.  

Даже в учебном Olist данные обезличены — привыкайте думать о чувствительности с первого дня.

---

## 8.9. Data Discovery

**Discovery** — как потребитель находит нужные данные:

- поиск по catalog;  
- глоссарий;  
- рекомендации / популярные витрины;  
- документация dbt.  

Плохой discovery → появление дублей витрин и «теневая аналитика» в Excel.

---

## 8.10. DataHub / OpenMetadata / Microsoft Purview

| Платформа | Кратко |
|-----------|--------|
| **DataHub** | Open-source catalog + lineage, сильный push-модель метаданных |
| **OpenMetadata** | Open-source, UI, качество, lineage, ownership |
| **Microsoft Purview** | Enterprise governance в экосистеме Microsoft |

Для курса: доп. баллы. Минимум — продемонстрировать lineage через dbt docs / схему зависимостей.

---

## Ключевые выводы

1. Metadata делает данные находимыми и понятными.  
2. Lineage связывает KPI с источниками.  
3. Ownership и governance — организационная основа доверия.  
4. Доступ и PII — часть DataOps, не «отдельная безопасность потом».
