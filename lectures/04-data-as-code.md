# Глава 4. Data as Code и управление версиями

## Цели главы

- Понять Analytics / Data as Code  
- Настроить работу с Git для SQL, Python и конфигов  
- Освоить branching, PR и code review в data-команде  
- Связать IaC и воспроизводимость  

---

## 4.1. Analytics as Code

**Analytics as Code** — аналитическая логика (SQL-модели, метрики, тесты, документация) хранится и развивается **как программный код**.

Следствия:

- история изменений;  
- review перед продом;  
- воспроизводимая сборка витрин;  
- отказ от «поправил в проде руками».  

Инструменты-якоря: **dbt** (`ref`, `source`, `schema.yml`), SQL-файлы в Git, макросы, seeds.

Антипаттерн: единственная копия правды — запрос в BI-инструменте без версии.

---

## 4.2. Зачем Git в Data Engineering

Git даёт ответы:

- *кто* изменил расчёт revenue;  
- *когда* и *зачем* (commit message / PR);  
- *как откатиться*;  
- *что именно* ушло в CI и prod.  

Без Git data-команда работает в режиме «археологии по серверам».

Минимальный процесс курса:

```text
Issue → Branch → Commit → Pull Request → CI → Review → Merge
```

---

## 4.3. Version Control для SQL и Python

**SQL (модели dbt):**

- один файл ≈ одна модель;  
- осмысленные имена (`fct_orders.sql`, `mart_sales_daily.sql`);  
- не хранить секреты и полные дампы.  

**Python (ingestion):**

- модули загрузки по источникам;  
- зависимости в `requirements.txt` / lock-файле;  
- тесты на идемпотентность и парсинг.  

Практика: маленькие коммиты с ясным «почему», не «fix stuff».

---

## 4.4. Версионирование конфигураций

Конфиги тоже код:

- `profiles.yml` / `dbt_project.yml` (без паролей);  
- Airflow Variables через secrets backend / env;  
- `docker-compose.yml`, Dockerfile;  
- `.env.example` в Git, `.env` — локально.  

Правило: **секреты не коммитить**. В Git — структура и примеры.

Изменение расписания DAG или переменных окружения — через PR, если это влияет на поведение прода.

---

## 4.5. Версионирование схем данных

Схема эволюционирует: rename колонки, новые поля, смена типов.

Подходы:

1. **Миграции** (Flyway, Liquibase, Alembic) — версионированные up/down.  
2. **Контракты** — ожидаемая схема на границе систем.  
3. **Тесты схемы** в CI — fail при breaking change.  
4. **Expand/contract** — сначала добавить новое, переключить потребителей, удалить старое.  

Сценарий курса «`price` → `product_price`»: обнаружение → фикс в коде → PR → CI → восстановление pipeline.

---

## 4.6. Branching и Pull Request

Рекомендуемая модель для учебного/небольшого проекта:

- `main` — то, что можно деплоить;  
- ветка `feature/...` или `fix/...` на задачу;  
- PR обязателен;  
- merge после зелёного CI.  

Для команд больше:

- `develop` / GitFlow — по необходимости, не усложнять без нужды;  
- protected branches.  

Прямой push в `main` на курсе **не рекомендуется**.

---

## 4.7. Code Review

Что смотреть в data-PR:

| Вопрос | Пример |
|--------|--------|
| Корректна ли бизнес-логика? | revenue с возвратами или без? |
| Есть ли тесты? | unique, not_null, relationships |
| Идемпотентность? | incremental ключи |
| Производительность? | лишние full-scan |
| Документация? | description в schema.yml |
| Безопасность? | нет секретов, нет лишнего PII |

Review — не формальность: это главный «человеческий тест» до прода.

---

## 4.8. Infrastructure as Code

**IaC** — инфраструктура описывается кодом: Docker Compose, Terraform, Ansible, Kubernetes manifests.

Зачем DataOps:

- одинаковый Airflow/Postgres/dbt у всех;  
- быстрый подъём стенда;  
- меньше «снежных комков» ручных серверов.  

В курсе минимум: `docker compose up` поднимает ключевые сервисы.

---

## 4.9. Воспроизводимость изменений

Изменение воспроизводимо, если другой человек (или CI) может:

1. взять тот же commit;  
2. поднять окружение по инструкции;  
3. прогнать те же команды;  
4. получить тот же логический результат (с учётом данных периода).  

Чеклист воспроизводимости:

- pinned зависимости;  
- документированный запуск;  
- нет скрытых ручных шагов;  
- данные-источники описаны (см. DATA_SOURCES);  
- секреты через env.  

---

## Ключевые выводы

1. Аналитика без Git — не DataOps.  
2. Версионируются код, конфиги и схемы.  
3. PR + review + CI — стандартный путь в prod.  
4. IaC и Docker делают окружения повторяемыми.
