# Глава 9. Построение DataOps в организации

## Цели главы

- Понять operating model и роли  
- Связать Data Products, Self-Service и Data Mesh с DataOps  
- Знать метрики и модели зрелости  
- Увидеть end-to-end кейс внедрения  

---

## 9.1. DataOps Operating Model

**Operating model** отвечает:

- кто что делает;  
- как идут изменения;  
- какие стандарты обязательны;  
- как измеряется успех.  

Элементы:

- платформенная команда (рельсы: CI, оркестрация, observability);  
- доменные команды (витрины и продукты данных);  
- процессы PR / инцидентов / контрактов;  
- обучение и гильдии практик.  

DataOps внедряется не «установкой Airflow», а согласованием этой модели.

---

## 9.2. Роли и ответственность

RACI-мышление полезно для критичных витрин:

- **Responsible** — делает pipeline;  
- **Accountable** — отвечает за результат перед бизнесом;  
- **Consulted** — согласует определение метрики;  
- **Informed** — получает статус SLA.  

Без явных ролей инциденты превращаются в пинг-понг.

---

## 9.3. Data Engineer / Analyst / Data Scientist / Platform Engineer

| Роль | Фокус |
|------|--------|
| **Data Engineer** | Ingestion, модели, пайплайны, качество |
| **Analyst** | Метрики, ad-hoc, потребление mart, требования |
| **Data Scientist** | Модели ML, фичи, эксперименты |
| **Platform Engineer** | Airflow/K8s/CI, самообслуживание, стандарты |

В маленькой команде роли совмещаются; в зрелой — разделяются, но работают в одном Git/процессе.

---

## 9.4. Data Owner и Data Steward

**Data Owner** — бизнес-владелец домена (например, «Заказы»): приоритеты, определения, приемка.

**Data Steward** — хранитель качества и правил: справочники, DQ-политики, классификация.

Технический владелец пайплайна не заменяет бизнес-owner’а определения «что такое возврат».

---

## 9.5. Data Products

**Data Product** — версионируемый продукт с:

- потребителями;  
- контрактом / SLA;  
- документацией;  
- владельцем;  
- измеримым качеством.  

Витрина `mart_sales_daily` — кандидат в data product, если к ней есть договорённости, а не «просто таблица в схеме».

Мышление продуктом сдвигает фокус с «загрузить всё» на «поставить ценность».

---

## 9.6. Self-Service Data Platform

Цель self-service: аналитик/домен может **безопасно** создавать и публиковать данные без тикета на каждую колонку.

Платформа даёт:

- шаблоны репозиториев;  
- CI из коробки;  
- окружения;  
- catalog + доступ;  
- стандарты тестов.  

Баланс: свобода доменов + центральные guardrails (безопасность, DQ минимум, нейминг).

---

## 9.7. Data Mesh и DataOps

**Data Mesh** — организационный подход: доменная ответственность за data products, self-serve platform, federated governance.

| Data Mesh | DataOps |
|-----------|---------|
| Кто владеет данными (домены) | Как надёжно поставлять и менять данные |
| Продуктовое мышление | Инженерные практики CI/CD/DQ/obs |

Они дополняют друг друга: Mesh без DataOps → хаос доменов; DataOps без доменного владения → центральный bottleneck.

---

## 9.8. Метрики DataOps

Примеры метрик здоровья практики:

| Метрика | Смысл |
|---------|--------|
| Pipeline success rate | Надёжность поставки |
| Data freshness (breach count) | Актуальность |
| Test pass rate | Качество |
| Lead time for change | Скорость поставки изменений |
| Deployment frequency | Темп релизов |
| MTTR | Скорость восстановления |
| % активов с owner + docs | Зрелость governance |

Не собирайте 50 метрик — начните с 4–5, связанных с болями организации.

---

## 9.9. DataOps Maturity Model

Уровни (упрощённо):

| Уровень | Характеристика |
|---------|----------------|
| 0 Ad-hoc | Скрипты, ручные выгрузки |
| 1 Repeatable | Пайплайны есть, мало тестов |
| 2 Managed | Git, CI, базовый DQ |
| 3 Measured | SLO, observability, MTTR |
| 4 Optimizing | Контракты, self-service, продукты данных |

Курсовой проект целится примерно в уровни **2–3** на учебном периметре.

Оценка зрелости нужна, чтобы выбрать следующий шаг, а не «внедрить всё сразу».

## 9.10. End-to-End кейс внедрения DataOps

### Контекст

Интернет-магазин: отчёты опаздывают, SQL правят в проде, возвраты иногда не доезжают, бизнес не доверяет revenue.

### Шаги внедрения

1. **Зафиксировать боль и SLA** — «продажи вчера к 08:00».  
2. **Собрать sources** — OLTP Postgres, API остатков, CSV returns.  
3. **Построить слои** — RAW→STAGING→CORE→MART в dbt.  
4. **Оркестрация** — Airflow DAG с retry и DQ gate.  
5. **Git + PR** — запрет прямых правок prod-логики.  
6. **CI** — compile + tests на каждый PR.  
7. **Observability** — success, duration, row_count, freshness.  
8. **Lineage + docs** — dbt docs, README, ownership витрин.  
9. **Аварийные учения** — orphan FK, missing file, rename колонки.  
10. **Измерить** — success rate, lead time, trust к дашборду.  

### Результат

Не «много инструментов», а управляемый цикл:

```text
Sources → Ingestion → RAW → STAGING → CORE → MART → BI
+ Git + CI/CD + Tests + DQ + Monitoring + Lineage + Docs
```

Это и есть практический итог дисциплины.

---

## Ключевые выводы

1. DataOps — это operating model, роли и метрики, а не только стек.  
2. Data products и self-service масштабируют поставку ценности.  
3. Mesh и DataOps усиливают друг друга.  
4. Зрелость растёт постепенно; курсовой проект — учебный end-to-end контур.
