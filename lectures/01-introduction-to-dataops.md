# Глава 1. Введение в DataOps

## Цели главы

- Понять, что такое DataOps и зачем он появился  
- Отличить DataOps от DevOps и MLOps  
- Знать принципы DataOps Manifesto  
- Увидеть, какие проблемы решает DataOps на практике  

---

## 1.1. Что такое DataOps

**DataOps** (Data Operations) — подход к управлению данными, который объединяет практики Agile, DevOps и статистического контроля процессов применительно к аналитике и data engineering.

Коротко: DataOps — это способ сделать работу с данными **быстрой, надёжной, воспроизводимой и наблюдаемой**, как современная разработка ПО.

DataOps охватывает:

- проектирование и эксплуатацию data pipelines;
- контроль качества данных;
- автоматизацию тестирования и доставки изменений;
- мониторинг и observability;
- совместную работу инженеров, аналитиков и бизнеса.

DataOps — это не один инструмент и не «ещё один слой в архитектуре». Это **операционная модель** и набор практик вокруг данных.

---

## 1.2. Почему появился DataOps

Рост объёмов данных и числа потребителей (BI, ML, продукт, финансы) столкнулся с устаревшими процессами:

| Было типично | Что ломалось |
|--------------|--------------|
| Ручные выгрузки и Excel | Невоспроизводимость, ошибки |
| «Скрипт на сервере» без Git | Непонятно, что в проде |
| Отчёты «к понедельнику» | Долгий цикл изменений |
| Качество проверяют глазами | Баги находят пользователи |
| Нет мониторинга свежести | Решения на устаревших данных |

DataOps появился как ответ на разрыв между **скоростью бизнеса** и **скоростью / качеством поставки данных**.

Триггеры:

1. Цифровизация и real-time ожидания  
2. Рост числа источников и потребителей  
3. Успех DevOps в разработке ПО — желание перенести практики на данные  
4. Регуляторика и требования к прозрачности происхождения данных  

---

## 1.3. Проблемы традиционной работы с данными

Типичные симптомы «до DataOps»:

1. **Силосность** — данные в разных системах, нет единого процесса.  
2. **Ручной труд** — загрузки, правки SQL «на проде», копии файлов.  
3. **Поздние ошибки** — брак виден уже в отчёте или дашборде.  
4. **Нет версий** — нельзя откатить аналитическую логику.  
5. **Нет тестов** — изменения не проверяются автоматически.  
6. **Слабый lineage** — непонятно, откуда взялся KPI.  
7. **Нет freshness-контроля** — отчёт «есть», но данные за вчера не доехали.  
8. **Долгий time-to-insight** — от идеи метрики до продакшена — недели.  

DataOps нацелен устранять эти проблемы системно, а не точечными «костылями».

## 1.4. DataOps vs DevOps vs MLOps

| | **DevOps** | **DataOps** | **MLOps** |
|---|------------|-------------|-----------|
| Объект | Приложения, сервисы | Данные, pipelines, витрины | Модели ML |
| Артефакты | Код, образы, конфиги | SQL/Python, схемы, тесты данных | Модели, фичи, эксперименты |
| Качество | Unit/e2e тесты | Data quality, contracts | Offline/online metrics |
| Доставка | CI/CD приложения | CI/CD pipelines + миграции схем | Train → validate → deploy |
| Специфика | Latency, uptime сервиса | Freshness, volume, schema drift | Drift модели, retrain |

Связь:

```text
DevOps  →  культура автоматизации и CI/CD
   ↓
DataOps →  то же для данных и аналитики
   ↓
MLOps  →  то же + жизненный цикл моделей (часто опирается на DataOps)
```

Хороший MLOps без зрелого DataOps обычно буксует: модели едят плохие или «тихие» данные.

## 1.5. Связь с Agile и Lean

**Agile** даёт короткие итерации, обратную связь, приоритезацию ценности.

В DataOps:

- небольшие изменения витрин / пайплайнов;
- частые релизы через PR;
- демо ценности для бизнеса (метрика, дашборд).

**Lean** даёт устранение потерь (waste):

- ожидание данных;
- переделки из‑за плохого качества;
- ручная работа, которую можно автоматизировать;
- «лишние» копии данных без владельца.

Цель: **сократить цикл** «потребность → надёжные данные в проде».

---

## 1.6. DataOps Manifesto

[DataOps Manifesto](https://dataopsmanifesto.org/) формулирует ценности сообщества. Ключевые идеи (обобщённо):

1. Удовлетворять потребности клиентов **непрерывно** поставкой аналитики.  
2. Ценить **работающую аналитику** выше красивых, но мёртвых документов.  
3. Принимать изменения требований — данные и бизнес меняются.  
4. Люди и взаимодействие важны; инструменты — средство.  
5. Ежедневное сотрудничество аналитиков, инженеров и заказчиков.  
6. Доверять командам и давать им среду для экспериментов.  
7. Простота и устранение лишней сложности.  
8. Ориентация на устойчивый темп поставки.  
9. Рефлексия и улучшение процессов.  

Манифест — ориентир культуры, а не чек‑лист технологий.

## 1.7. Основные принципы DataOps

Практический набор принципов:

| Принцип | Смысл |
|---------|--------|
| **Data as Code** | Трансформации, тесты, конфиги — в Git |
| **Автоматизация** | Ingestion, тесты, деплой, алерты — без ручных ритуалов |
| **Качество встроено** | Тесты на каждом этапе, не «в конце» |
| **Observability** | Видно здоровье пайплайнов и данных |
| **Воспроизводимость** | Один и тот же код → тот же результат в окружении |
| **Идемпотентность** | Повторный запуск безопасен |
| **Малые изменения** | Частые PR вместо «большого взрыва» |
| **Владение (ownership)** | У данных и продуктов есть ответственные |
| **Обратная связь** | От мониторинга и пользователей — в бэклог |

## 1.8. Примеры применения

**Интернет-магазин (как в курсовом проекте):**  
заказы из БД + API остатков + CSV возвратов → RAW/STAGING/CORE/MART → дашборд; CI ловит битые FK; алерт при отсутствии файла за день.

**Финтех:**  
ежедневные витрины риска к 07:00; SLA на freshness; schema migration через PR; rollback при падении тестов.

**Медиа / продукт:**  
события из Kafka → витрины продуктовой аналитики; контроль volume spike/drop; lineage метрики «retention» до сырого события.

**Enterprise:**  
единый catalog + ownership; self-service витрины для аналитиков; maturity model и метрики success rate пайплайнов.

---

## Ключевые выводы

1. DataOps — операционная модель поставки данных, а не «название стека».  
2. Он закрывает разрыв между скоростью бизнеса и качеством данных.  
3. Перенимает культуру DevOps/Agile/Lean, но добавляет специфику данных (freshness, schema, volume).  
4. Принципы: код в Git, автоматизация, тесты, observability, малые изменения.
