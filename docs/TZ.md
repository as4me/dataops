# Техническое задание: итоговый проект по дисциплине «Основы DataOps»

## 1. Общая информация

В рамках дисциплины «Основы DataOps» необходимо выполнить один сквозной командный или индивидуальный проект, демонстрирующий применение основных принципов DataOps при построении аналитической системы.

В течение курса проект последовательно развивается: от получения исходных данных и построения простого Data Pipeline до автоматизированной, тестируемой, наблюдаемой и воспроизводимой системы обработки данных.

Итоговая система должна реализовывать полный жизненный цикл данных:

```text
Источники данных → Загрузка → Хранение → Преобразование → Контроль качества → Публикация → Мониторинг → Аналитика
```

Одновременно необходимо реализовать инженерный контур:

```text
Git → CI/CD → Testing → Deployment → Monitoring → Documentation
```

---

## 2. Цель проекта

Цель проекта — спроектировать и реализовать DataOps-платформу для обработки и анализа данных интернет-магазина.

В рамках проекта необходимо продемонстрировать:

- работу с несколькими источниками данных;
- автоматизированную загрузку данных;
- построение Data Pipeline;
- оркестрацию процессов;
- управление версиями;
- применение подхода Analytics as Code;
- автоматизированное тестирование;
- контроль качества данных;
- CI/CD;
- мониторинг и Data Observability;
- документирование данных;
- Data Lineage;
- построение аналитических витрин;
- получение конечного аналитического результата.

---

## 3. Бизнес-сценарий

Рассматривается условная компания, управляющая интернет-магазином.

Компания работает с данными о:

- клиентах;
- товарах;
- заказах;
- составе заказов;
- платежах;
- возвратах;
- продавцах;
- остатках товаров;
- внешних факторах.

Данные поступают из нескольких информационных систем.

На начальном этапе компания сталкивается со следующими проблемами:

- часть данных загружается вручную;
- данные находятся в разных системах;
- отсутствует единый процесс обработки;
- ошибки обнаруживаются уже после построения отчетности;
- изменения SQL-кода не контролируются;
- отсутствует единый механизм тестирования;
- невозможно быстро установить источник ошибки;
- нет контроля свежести данных;
- нет автоматического мониторинга;
- происхождение аналитических показателей не документировано.

Необходимо построить DataOps-процесс, устраняющий указанные проблемы.

## 5. Источники данных

В проекте необходимо использовать минимум три различных типа источников.

### 5.1. Основной набор данных

Рекомендуемый источник:

**Olist Brazilian E-Commerce Public Dataset**

Открытый обезличенный набор данных интернет-магазина, содержащий информацию примерно о 100 тысячах заказов.

Датасет доступен на платформе Kaggle.

Основные сущности:

- customers;
- orders;
- order_items;
- products;
- sellers;
- payments;
- reviews;
- geolocation.

Рекомендуется загрузить исходные таблицы Olist в PostgreSQL и далее рассматривать PostgreSQL как операционную систему интернет-магазина.

```text
Olist Dataset
      │
      ▼
 PostgreSQL
      │
      ▼
Data Pipeline
```

### 5.2. REST API

В качестве внешнего API рекомендуется использовать:

**DummyJSON**

API может использоваться как источник:

- товаров;
- остатков;
- цен;
- рейтингов;
- информации о доступности товаров.

Пример логической структуры:

```text

price
stock
rating

```

Загрузка должна выполняться программно через HTTP-запрос.

### 5.3. Файловый источник

Необходимо реализовать обработку файлов, поступающих периодически.

Например:


Файлы могут содержать сведения о возвратах:


Допускается сформировать данные о возвратах самостоятельно на основе исходного датасета.

### 5.4. Дополнительный внешний источник

Для студентов, выполняющих расширенную версию проекта, рекомендуется подключить дополнительный API.

После этого возможно построение дополнительной аналитики влияния внешних факторов на продажи или доставку.

## 9. Data Ingestion

Необходимо разработать процессы получения данных минимум из трёх источников.

```text
PostgreSQL
     │
     ├─────────────┐
     │             │
REST API ──────────┼──→ Ingestion → RAW
     │             │
CSV Files ─────────┘
```

Pipeline должен:

- получать данные;
- сохранять дату и время загрузки;
- регистрировать источник;
- фиксировать количество загруженных записей;
- обрабатывать ошибки;
- поддерживать повторный запуск.

Повторное выполнение процесса не должно приводить к неконтролируемому появлению дубликатов.

Необходимо продемонстрировать принцип **Idempotency**.

## 11. Моделирование данных

Преобразование данных необходимо реализовать преимущественно через dbt.

Рекомендуемая архитектура:

```text
RAW → STAGING → CORE → MART
```

### 11.1. STAGING

На данном уровне выполняются:

- приведение типов;
- очистка;
- переименование полей;
- стандартизация;
- первичная обработка NULL;
- удаление технических ошибок.

Примеры: `stg_customers`, `stg_orders`, `stg_products`, `stg_returns`.

### 11.2. CORE

На уровне CORE формируется единая бизнес-модель.

Примеры: `dim_customer`, `dim_product`, `dim_seller`, `fact_orders`, `fact_order_items`, `fact_returns`.

### 11.3. MART

На уровне MART создаются таблицы, предназначенные непосредственно для аналитики.

Необходимо создать **минимум три** аналитические витрины.

## 17. Data Quality

В проекте необходимо реализовать автоматические проверки качества данных.

Минимальное количество: **10 тестов**.

Необходимо проверить несколько различных измерений качества.

### 17.1. Completeness

Например: `order_id IS NOT NULL`.

### 17.2. Uniqueness

Например: `order_id`, `customer_id`, `product_id` должны быть уникальными там, где это предусмотрено моделью.

### 17.3. Referential Integrity

Например: `orders.customer_id` должен существовать в `customers.customer_id`.

### 17.4. Validity

Например: `quantity > 0`, `price >= 0`, `refund_amount >= 0`.

### 17.5. Freshness

Необходимо контролировать, насколько актуальны загруженные данные.

### 17.6. Business Rules

Например:

- `return_date >= order_date`;
- `refund_amount <= order_amount`.

Студент может предложить дополнительные бизнес-правила.

## 18. Data Observability

Необходимо реализовать базовый контроль состояния системы.

Следует отслеживать минимум:

- успешность pipeline;
- время запуска;
- продолжительность;
- количество обработанных строк;
- количество ошибок;
- freshness;
- существенное изменение объема данных.

Например, если обычно система получает 100 000 записей, а при очередной загрузке — 1 000 записей, это должно рассматриваться как потенциальная проблема.

## 19. SLA, SLO и показатели надежности

Студент должен определить минимум один **SLA** и один **SLO**.

Пример SLA: данные за предыдущий день должны быть готовы к использованию до 08:00.

Пример SLO: не менее 99% ежедневных запусков Data Pipeline должны завершаться успешно.

Дополнительно можно использовать: MTTR, pipeline success rate, data freshness, test pass rate, deployment frequency.

## 23. Аварийные сценарии

В рамках проекта необходимо продемонстрировать реакцию системы минимум на три вида проблем.

### Сценарий 1. Ошибка качества

В таблице orders появляется `customer_id`, которого нет в customers.

Необходимо показать:

- обнаружение ошибки;
- какой тест сработал;

Необходимо показать, каким образом система обнаруживает отсутствие свежих данных.

### Сценарий 3. Schema Change

В источнике происходит изменение схемы (например, `price` → `product_price`).

Необходимо продемонстрировать:

1. возникновение проблемы;

4. исправление;
5. изменение кода;

## 30. Что оценивается в первую очередь

Главной целью проекта является не использование максимального количества инструментов.

Оценивается способность студента построить **системный DataOps-процесс**.

Важно уметь объяснить:

- почему была выбрана конкретная архитектура;
- как данные перемещаются между компонентами;
- как контролируется качество;
- как обнаруживается ошибка;
- как изменение кода попадает в Production;
- как можно воспроизвести систему;
- как определить источник аналитического показателя;
- что произойдет при сбое;
- каким образом система восстанавливается.

Итоговый проект должен демонстрировать не отдельный ETL-скрипт, а полный управляемый жизненный цикл данных.
